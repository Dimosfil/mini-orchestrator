# Software Evaluation Framework

Last reviewed: 2026-06-30

## Purpose

Mini Orchestrator evaluations are acceptance checks for software artifacts
generated by agent workflows. They are not a replacement planner, executor, or
provider layer. Evaluation may start or observe an existing Mini Orchestrator
workflow, then verifies the generated project as runnable software.

The framework answers:

- Did the agent workflow produce the expected application artifact?
- Does the artifact have the expected files and structure?
- Do project commands, tests, servers, HTTP checks, and log scans pass within a
  bounded execution policy?
- What evidence should a human reviewer or later LLM judge inspect?

## Ownership

Mini Orchestrator remains the owner of task cards, chain presets, workflow
approval, and execution-mode routing. Evaluations sit above that runtime:

```text
Eval Suite
  -> Eval Runner
  -> Existing Mini Orchestrator workflow or existing artifact
  -> Artifact Locator
  -> Software Evaluators
  -> Runtime report
```

All model calls must go through existing Mini Orchestrator Dispatcher/Symphony
paths. Evaluators must not call OpenAI, Anthropic, Gemini, or any other model
provider directly.

## Runtime Entities

- `eval_suites`: saved evaluation definitions and case/check configuration.
- `eval_runs`: one execution of a suite or one selected case.
- `eval_artifacts`: the generated or selected project directory under review.
- `eval_results`: one row per check result.
- `eval_reports`: compact pass/fail report for UI, CLI, and handoff use.

Evaluation results are runtime/generated state. Source definitions, schemas,
tests, and code are reviewable source; concrete run outputs remain in SQLite or
generated artifact folders.

## Suite Shape

An eval suite contains one or more cases. Each case can reference a generated
artifact path directly or describe a task to be run by a future workflow adapter.

```json
{
  "id": "web-app-basic",
  "name": "Basic web app acceptance",
  "cases": [
    {
      "id": "todo-app",
      "task": "Create a todo web app with add, complete, and delete actions.",
      "artifactPath": ".mini_orchestrator/test-runs/todo-app",
      "checks": [
        {"id": "package-json", "type": "file_exists", "path": "package.json"},
        {"id": "tests", "type": "test_pass", "command": ["python", "-m", "pytest"]},
        {"id": "home", "type": "http_check", "url": "http://127.0.0.1:5173/"}
      ]
    }
  ]
}
```

## Artifact Locator

The runner locates an artifact in this order:

1. Explicit runtime override supplied to the runner or API.
2. Case-level `artifactPath`.
3. Case-level `artifact.path`.
4. Case-level `expectedArtifacts.projectDir`.
5. Workflow-result artifact hints when a workflow adapter is used.
6. Existing fallback `.mini_orchestrator/test-runs/<suite-id>/<case-id>`.

Artifact paths must resolve inside the current project root for this local
runtime. If a path is missing or escapes the root, the evaluation records a
failed artifact result instead of silently inspecting another project.

## Execution Policy

Command and server checks execute generated code, so the first implementation is
intentionally bounded:

- command cwd must stay inside the artifact directory;
- commands run without a shell;
- dangerous command markers remain blocked by `command_adapter`;
- only common project/test executables are allowed by default;
- every command has a timeout and captured-output limit;
- server checks terminate the spawned process after the check;
- reports store snippets and metadata, not unbounded logs.

## Evaluator Layers

Initial evaluators:

- `file_exists`
- `directory_exists`
- `json_valid`
- `file_contains`
- `command`, `build_pass`, `test_pass`
- `server_start`
- `http_check`
- `log_scan`
- `artifact_manifest_check`

Later layers:

- browser smoke checks;
- screenshot sanity and visual comparison;
- baseline/regression compare;
- LLM-as-a-Judge over evidence only;
- CI/CD integration.

## Pass/Fail Policy

A report is `passed` only when all required checks pass. Missing artifacts,
unsafe paths, blocked commands, timeouts, HTTP failures, and invalid JSON are
`failed` results. Unsupported checks are failed in MVP so suite authors see the
gap immediately.
