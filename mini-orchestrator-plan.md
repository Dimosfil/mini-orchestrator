# План сборки мини‑оркестратора для Codex (GPT‑5.5 + GPT‑5.3‑Codex‑Spark)

## 0) Цель
- Собрать минимальный оркестратор, где:
  - **GPT‑5.5** принимает решение, строит план и контролирует качество.
  - **GPT‑5.3‑Codex‑Spark** исполняет технические шаги (поиск/чтение/правки/проверки).
- Результат: воспроизводимый цикл `план → выполнение → сверка → ответ`.

## 1) Архитектурная схема
- Оркестратор API/скрипт с тремя слоями:
  1. **Router** — определяет тип задачи и модель.
  2. **Planner (GPT‑5.5)** — делает по шагам план и критерии завершения.
  3. **Executor (GPT‑5.3‑Codex‑Spark)** — выполняет шаги через безопасный инструментальный слой.
  4. **Validator (GPT‑5.5)** — проверяет промежуточный результат и решает продолжение.
- Формат обмена:
  - JSON-сообщение с полями: `request_id`, `goal`, `state`, `next_action`, `model`, `tool`, `status`, `result`, `need_routing_check`, `attempt`.

## 2) Роли и обязанности
- **GPT‑5.5 (координатор)**
  - Классифицирует задачу по сложности/рискам.
  - Формирует/обновляет план.
  - Решает продолжать ли цикл или завершать.
  - Обрабатывает ошибки и выбирает стратегию повторов.
- **GPT‑5.3‑Codex‑Spark (исполнитель)**
  - Выполняет конкретные шаги (чтение/поиск/правка/проверка).
  - Возвращает структурированный отчёт о каждом шаге.
  - Не принимает решение о смене общей стратегии.

## 3) Алгоритм оркестрации (MVP)
1. Получение запроса от пользователя.
2. Нормализация входа (цель + ограничения).
3. Маршрутизация:
   - простые/высоко‑рисковые/инженерные задачи → `GPT‑5.5`
   - рутинные технические шаги → `GPT‑5.3‑Codex‑Spark`.
4. GPT‑5.5 создает план из 5–12 шагов и критерии успеха.
5. Для каждого шага:
   - если нужен инструмент → передать шаг в GPT‑5.3.
   - дождаться результата.
   - валидация через GPT‑5.5 и возможный корректирующий план.
6. Ограничение цикла:
   - `max_iterations` и `max_retries` (например 12 и 3).
7. Финальная агрегация:
   - итоговый ответ + список выполненных шагов + риск/неуверенность.

## 4) Инструментальный слой
- Allowlist инструментов:
  - `read_file`, `search`, `apply_patch`, `run_command`.
- Для каждого инструмента:
  - строгие границы путей,
  - лимиты по времени,
  - ограничение размера вывода.
- Все изменения логировать в JSON журнал.

## 6) Риски и как закрыть
- **Риск:** зацикливание модели.  
  - Защита: счетчик итераций + hard stop.
- **Риск:** плохая передача контекста между шагами.  
  - Защита: короткое сжатие состояния после каждого шага.
- **Риск:** чрезмерные права инструментов.  
  - Защита: allowlist + ограниченные директории + подтверждение критичных операций.
- **Риск:** «мягкие» ошибки (нет результата, но статус=успех).  
  - Защита: обязательная валидация по явным критериям.

## 7) Что будет готово после запуска
- Конфигурируемый `orchestrator` с двумя моделями.
- Поведенческая трассировка каждой итерации.
- Минимальная пригодная версия, которую можно расширять на прод‑режим.

## 8) Release Readiness Contract (v1.0)

Цель: определить и зафиксировать минимально-необходимый релизный контракт.

### Runtime contract
- Install command: `python -m pip install -e .` (или `python -m venv .venv; .\.venv\Scripts\Activate.ps1; python -m pip install -e .`).
- Run command (CLI): `python -m mini_orchestrator "<request>"`.
- UI command (opt-in): `python -m mini_orchestrator --ui`.
- Smoke test command: `python -m mini_orchestrator "search AGENTS"`.
- Health endpoints (если включён UI): `/health`, `/api/run`.
- Build command: пока не определена; документировать как `No build pipeline yet` до появления.

### Environment contract
- Python runtime и зависимости должны устанавливаться в editable режиме.
- `OPENAI_API_KEY` опционален; при его отсутствии система обязана работать в детерминированном fallback режиме.
- `MINI_ORCHESTRATOR_LLM_PROVIDER` поддерживает значения: `auto|openai|rules|off`.
- При включении LLM должны быть документированы и переопределяемы `MINI_ORCHESTRATOR_COORDINATOR_MODEL` и `MINI_ORCHESTRATOR_EXECUTOR_MODEL`.

### Functional release criteria (MVP)
- Единый путь выполнения: request -> parse -> plan -> execute -> validate -> final status.
- Никакой запрос не должен застревать в `needs_routing_check` для поддерживаемых интентов.
- Для неизвестных/неподдерживаемых запросов возвращается понятный `respond`.
- UI отражает переход статусов и финальный статус задачи.
- Ошибки зависимости от внешних служб (`config-service`, `Symphony`) должны быть явными.

### Release done definition
