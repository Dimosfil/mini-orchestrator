# Mini Orchestrator: подробное руководство

[English](README.extended.md) · **Русский** · [Краткий README](../README.ru.md)

## Цель проекта

Mini Orchestrator — небольшая среда для экспериментов с настраиваемыми
AI-воркфлоу. Основной принцип проекта: план должен быть виден пользователю,
запуск требует явного подтверждения, передачи между агентами можно проверить, а
результат не становится финальным до ручной приёмки.

Проект управляет карточками задач, настройкой workflow, подтверждениями,
маршрутизацией, хранением состояния, лимитами и Human Review. Dispatcher и
Symphony выступают адаптерами исполнения внутри этого жизненного цикла.

## Основной сценарий

1. Введите задачу, например `оркестратор план Сделай калькулятор`.
2. Запросите предварительный план от реального агента-планировщика.
3. Проверьте план и технические данные.
4. Явно подтвердите план.
5. Выберите сохранённый пресет цепочки и запустите workflow.
6. Следите за этапами и результатами в Live Runs.
7. Примите результат в Human Review или отправьте его на доработку.

Стандартный пресет `планировщик -> исполнитель -> ревьюер` показывает принцип
работы, но не зашит в архитектуру. В проверенном пресете можно изменить число и
порядок агентов, роли, модели, уровень reasoning, режим доступа и рабочие пакеты.

## Основные части продукта

### Главная панель и Live Runs

Главная панель управляет подтверждённым запуском. Одна карточка задачи
сохраняется на протяжении всего процесса и показывает состояние этапов,
последние события, краткие результаты, выбранную цепочку и решение ревьюера.
Live Runs поддерживает режимы Dispatcher, Symphony и Combined.

### Конструктор агентов

Визуальный конструктор создаёт карточки агентов и связи между ними. Черновик и
импорт могут временно находиться в `localStorage`, а именованные схемы и пресеты
цепочек сохраняются бэкендом. Перед компиляцией пользователь проверяет манифест:
задачу, порядок агентов, модели, reasoning, режимы доступа, политику рабочей
папки и краткое описание первого промпта.

Компиляция проверяет и фиксирует конфигурацию, но не запускает воркеры. Запуск
по-прежнему выполняется из главной панели после подтверждения.

### Human Review

Успешные результаты и результаты со статусом `needs_changes` сначала попадают в
Human Review. Пользователь принимает работу в Done или отправляет её на
доработку. Финальный статус в WorkNest передаётся только после такой приёмки.

### Наборы оценок

Бэкенд умеет сохранять и запускать наборы проверок программных артефактов. Это
отдельный слой верификации результата, который не заменяет подтверждение и
управление жизненным циклом задачи.

## Режимы исполнения

### Dispatcher

Dispatcher выполняет выбранный пресет через воркеры Codex app-server. Просмотр
плана и подтверждённый запуск разделены:

```powershell
python tools\codex-dispatcher\dispatcher.py --task "<задача>" --plan-only
python tools\codex-dispatcher\dispatcher.py --task "<задача>" --chain
```

Для настоящего проектного `gi test` используйте локальный runner, чтобы он
учитывал сохранённые настройки панели:

```powershell
python tools\run_gi_test.py --task "<задача релизной или полной проверки>"
```

### Symphony

Приём задач в Symphony разрешён только через проверенный контракт. В основном
сценарии Mini Orchestrator продолжает владеть карточкой задачи, чек-листом,
порядком цепочки и состоянием. Он передаёт Symphony одного агента за раз,
дожидается сохранённого результата и добавляет структурированный контекст к
следующему этапу.

Если в записи Symphony нет документированного intake endpoint, Mini Orchestrator
создаёт видимый заблокированный запуск, а не сообщает об успешном приёме задачи.

### Встроенное ядро

В пакете также есть компактный цикл `plan -> execute -> validate`:

```powershell
python -m mini_orchestrator "search AGENTS"
```

LLM-координатор здесь необязателен и может переключиться на правила. Этот путь
подходит для экспериментов с ядром, но отделён от пресетов главной панели.

## Runtime и хранение данных

Основное состояние проекта хранится в:

```text
.mini_orchestrator/runtime.sqlite3
```

В SQLite находятся сохранённые схемы, неизменяемые манифесты, задачи Dispatcher,
вывод процессов, карточки агентов, пресеты цепочек, профили воркеров, оценки и
состояние шлюза Symphony. Генерируемые тестовые артефакты остаются в файловой
папке `.mini_orchestrator/test-runs/`.

Канонический runtime скомпилированных манифестов проходит по явным веткам
успеха и ошибки, создаёт структурированные артефакты этапов, ограничивает
повторы, доработки и объём контекста, а также сохраняет переходы для продолжения
после прерывания.

Старые runtime-файлы можно импортировать командой:

```powershell
python tools\migrate_runtime_to_sqlite.py
```

Флаг `--prune-files` следует использовать только после успешного импорта и
проверки.

## Зависимости от сервисов

Интерфейс запускается по правилам GI config-service. Mini Orchestrator получает
свою запись через:

```text
GET /services/mini-orchestrator
```

Запись должна содержать `baseUrl`, `endpoints.availability` и `endpoints.api`.
Если конфигурация недоступна, приложение останавливается и не угадывает запасной
host или port.

Локальный выбор runtime хранится в:

```text
tools/project-memory/service-runtime.json
```

Для полной панели также требуется доступный сервис Symphony. Если он недоступен,
комбинированный операционный запуск считается незавершённым, но данные
Dispatcher всё равно остаются видны в Combined.

WorkNest служит внешним источником задач и получателем финального статуса. Мост
к нему ограничен документированными операциями получения задачи и завершения,
которые разрешаются через config-service.

## Установка и запуск

Требования: Python 3.10+, зависимости проекта и корректные записи сервисов GI.

```powershell
python -m venv .venv
. .venv\Scripts\Activate.ps1
python -m pip install -e .
python -m mini_orchestrator --ui
```

Дополнительные параметры UI:

- `--host` — ожидаемый host, совпадающий с config-service;
- `--port` — ожидаемый port, совпадающий с config-service;
- `--open-browser` — открыть интерфейс после запуска.

## Настройки

Основные переменные окружения:

- `OPENAI_API_KEY`;
- `MINI_ORCHESTRATOR_LLM_PROVIDER` (`auto`, `openai`, `rules` или `off`);
- `MINI_ORCHESTRATOR_COORDINATOR_MODEL`;
- `MINI_ORCHESTRATOR_EXECUTOR_MODEL`;
- `MINI_ORCHESTRATOR_OPENAI_BASE_URL`;
- `MINI_ORCHESTRATOR_DAEMON_STATE_URL`;
- `MINI_ORCHESTRATOR_SYMPHONY_SERVICE_ID`;
- `MINI_ORCHESTRATOR_DISPATCHER_STALE_AFTER_SECONDS`.

Настоящие секреты нельзя добавлять в Git. Локальные env-файлы должны оставаться
локальными.

## Обзор API

| Область | Основные endpoints |
|---|---|
| Проверка и контракт | `GET /health`, `GET /agent/guide`, `GET /agent/contract` |
| Встроенный workflow | `POST /api/run` |
| Dispatcher | `POST /api/dispatcher/plan`, `POST /api/dispatcher/run` |
| Карточки агентов | `POST /api/agents/chat`, `GET /api/agents/default-card`, `POST /api/agents/compile`, `POST /api/agents/run` |
| Сохранённые схемы | `GET/POST /api/agent-flows`, `GET/PUT /api/agent-flows/{id}`, `POST /api/agent-flows/{id}/validate`, `POST /api/agent-flows/{id}/compile` |
| Пресеты цепочек | `GET /api/agent-chain-presets`, `PUT/DELETE /api/agent-chain-presets/{id}` |
| Оценки | `GET/POST /api/evals/suites`, `POST /api/evals/run`, `GET /api/evals/runs` |
| Живое состояние | `GET /api/daemon/runs?source=combined|dispatcher|symphony` |
| Symphony | `POST /api/symphony/runs`, `POST /api/symphony/refresh`, `GET /api/symphony/issues/{issueIdentifier}` |
| WorkNest | `POST /api/worknest/claim`, `POST /api/worknest/complete` |

Для интеграций авторитетным источником служит строгий машиночитаемый контракт
`GET /agent/contract`.

## Наблюдаемость и ошибки

Техническая вкладка показывает runtime, путь к логу, решение диспетчера,
идентификаторы thread/turn воркеров, длительность, число событий и последние
компактные события. Полные промпты и ответы остаются в указанных логах.

Незавершённые запуски Dispatcher становятся `stale`, если процесс исчез или лог
не обновляется дольше заданного времени. Они исключаются из активного счётчика
и появляются в Human Review с причиной. Ошибки интеграции Symphony остаются
видимыми как заблокированные запуски шлюза.

## Текущие границы проекта

- Проект остаётся развивающейся экспериментальной лабораторией.
- Главная панель — активный интерфейс продукта.
- `launch-desk/` сохранён как устаревшее экспериментальное приложение и не
  входит в активный runtime.
- Визуальный конструктор создаёт и проверяет workflow, но не обходит
  подтверждение и сам по себе не запускает воркеры.
- Mini Orchestrator остаётся владельцем жизненного цикла, даже если работу
  агентов выполняет внешний адаптер.
